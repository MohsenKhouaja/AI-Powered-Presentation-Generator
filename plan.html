Auth Extraction: Duplicated in 3 Routers, Missing in Contexts

FILES
middleware/auth.ts api/presentations/router.ts:9-25 api/slides/router.ts:10-26 api/presentations_access/router.ts:9-25 api/contexts/router.ts:41-91 api/contexts/contexts-service.ts
PROBLEM

The authMiddleware at middleware/auth.ts already extracts the JWT and sets req.authenticatedUserId. Yet 3 out of 4 routers re-extract the token by duplicating the same 17-line getAuthenticatedUserId function. Each copy re-verifies the JWT and re-parses the payload — redundant work and a maintenance hazard. Meanwhile the contexts router has no auth check at all: it never reads userId and its service methods don't accept one, meaning any authenticated user can create/update contexts on any presentation.

Security gap: POST /api/contexts accepts presentationId from the request body with no ownership check. A user can attach context to any presentation.
SOLUTION

(1) Delete the 3 duplicate getAuthenticatedUserId functions. (2) Fix the 11 handlers to read req.authenticatedUserId from middleware instead. (3) Add userId parameter to contextService.create and update, verify presentation ownership. (4) Type req.authenticatedUserId so TS catches missing usage.

BENEFITS
→ Locality: auth extraction lives in exactly one module. Change the token format once.
→ Leverage: 11 handlers get the fix for free when the middleware changes.
→ Security: contexts module gains authorization, closing a real gap.
→ Depth: the middleware interface is "set userId on request" — deep. The duplicates are shallow (17 lines each with no added behaviour).

CANDIDATE 2 Strong

useEditorState — 403-line God Hook

FILES
frontend/src/components/editor/useEditorState.ts (403 lines)
PROBLEM

A single hook returning 60+ properties: 5 React Query mutations, 16 state variables, 4 refs (autosave timers, saving set, saved-notice timer, preview wrapper), drag-and-drop state management, preview scaling via ResizeObserver, context CRUD orchestration, share-invite logic, and autosave scheduling with 1200ms debounce. The interface is nearly as large as the implementation — this is a shallow module. Understanding any one flow (e.g., "what happens when the user presses Ctrl+S?") requires tracing through 10+ state variables across the file. Poor locality: a change to autosave timing could break drag-and-drop logic that lives in the same closure.

SOLUTION

Split into orthogonal sub-hooks, each with a small interface:

  • useSlideAutosave(slideId, content) — save scheduling + conflict detection
  • useSlideNavigation(slides, selectedIndex) — selection, add, delete
  • useDragReorder(slides) — drag state + drop handler
  • usePreviewScale(ref) — ResizeObserver wrapper
  • useEditorContext(presentationId) — context CRUD + AI generation
  • useEditorShare() — share dialog state + invite

Each sub-hook is deep: lots of internal behaviour behind a tiny interface. useEditorState becomes a thin composition layer.

BENEFITS
→ Locality: autosave bugs live in one file, drag-and-drop bugs in another. Fixes don't cascade.
→ Leverage: usePreviewScale could be reused for any scaled container, not just the editor.
→ Testability: each sub-hook has a small test surface. Mock one mutation per hook, not all 5.
→ Depth: each sub-hook hides internal complexity (timers, refs, state transitions) behind 2–4 parameters.

CANDIDATE 3 Worth exploring

AI Generation Tangled Inside Slides Service

FILES
backend/api/slides/slides-service.ts:46-183 backend/api/slides/slides-service.ts:416-490
PROBLEM

generateSlidesWithOpenRouter (138 lines) lives as a private function inside the slides service. It configures its own OpenAI client, builds a 90-line system prompt, implements JSON extraction/parsing, and normalises results. The AI concern is mixed with slide CRUD — a change to the prompt format requires editing the slides service file. The function is internally deep (lots of behaviour behind a single call) but it sits at the wrong seam.

Following the one-adapter rule: there's currently one AI provider (OpenRouter), so the seam is hypothetical. But the function's internal complexity (138 lines with system prompts, JSON parsing, base64 truncation, error handling) makes it a strong candidate for extraction.

SOLUTION

Extract into api/ai/ai-service.ts with a clean interface: 

interface AiGenerationInput {
  title: string;
  contextPrompt: string;
  files: ContextFileForPrompt[];
  numSlides?: number;
}

async function generatePresentationSlides(
  input: AiGenerationInput
): Promise

The slides service then depends on this via its interface; slidesService.generateFromContext calls aiService as a dependency.

BENEFITS
→ Locality: prompt engineering, JSON parsing, and model config live in one module. Slide CRUD and AI generation evolve independently.
→ Seam readiness: when a second AI provider is added, the seam becomes real. Tests can swap in a fake provider.
→ Testability: generatePresentationSlides can be tested in isolation with a mocked OpenAI client.

Dual-Database Slide Storage

FILES
backend/api/slides/slides-service.ts backend/api/presentations/presentations-service.ts backend/database/index.ts backend/database/drizzle/schema.ts:48-65
PROBLEM

Slide metadata (id, presentationId, slideOrder) lives in MySQL (Drizzle ORM). Slide content (the markdown body) lives in MongoDB. Every slide operation touches both databases with no transactional coordination:

  • create: MySQL insert + MongoDB insertOne — if MongoDB fails after MySQL, orphan row exists
  • removeOne: MySQL transaction (delete + reorder) + MongoDB deleteOne — if MongoDB fails, slide content leaks
  • generateFromContext: MySQL transaction + MongoDB insertMany — only the MySQL side is atomic
SOLUTION

Option A: Move slide content into MySQL as a TEXT column on the slides table, eliminating MongoDB entirely. This simplifies deployment (no MongoDB daemon) and enables real transactions.

Option B: Formalize MongoDB as the source of truth and use MySQL only as an index for ordering and relations. This inverts the current dependency direction.

BENEFITS (Option A)
→ Locality: all slide data in one database. One migration tool (Drizzle). One transaction boundary.
→ Testability: no MongoDB mocking needed for slide tests. Simpler test setup.
→ Deployment: remove MongoDB from docker-compose. One fewer stateful service to manage.
Contradicts the existing MongoDB usage spanning 5+ service files and the collection in backend/database/index.ts. Worth reopening only if the deployment complexity of MongoDB is a real pain point.
